## 1. v1 study (read at `archive/v1-final`)

**How v1 did it** (v1 had no v1→v1 schema importer; the nearest thing is JSON export/import):
- `db/sqlite/portability.js` → `exportAll()` / `importAll(bundle)` — one transaction, `INSERT OR IGNORE`
  by `id`, counts `imported` / `skipped`. Also wiki, jobs, runs, self-memories (not core).
- `lib/routes/api-data.js`, `lib/handlers/data/dataHandlers.js` — the HTTP + WS entry points.
- `db/encrypt.js` + `db/sqlite/encryption.js` — a v1 DB file may be a **whole-file encrypted blob** at rest
  (`APERIO_DB_ENCRYPT`, key in the OS keychain). `isPlaintextSqlite()` checks the header.

**v1 `memories` columns** (`db/migrations-sqlite/001_core.sql`): `id, type, title, content, tags, importance,
created_at, updated_at, source` — **same names and checks as v2** — plus `tier, expires_at, lang, valid_from,
valid_until, confidence, pinned` (v2 has none of these).

**Best parts (keep):** one transaction; idempotent by `id` (a second run imports 0, skips N); a result with counts.

**Bad parts (drop / fix):**
- `importAll` dropped `created_at` / `updated_at`: every imported row got "now" (the plan says keep dates).
- `catch { /* memory may not exist */ }` on wiki sources — a silent drop (AP5).
- `INSERT OR IGNORE` skipped a row that failed a CHECK with no reason given (AP5).
- It never re-embedded: imported rows had no vector until a later reindex.

**Lessons that apply:** L-P03 (set scratch paths before import — a test must never touch a real DB) ·
L-C18 / TR16 (DB encryption) · AP3 (the v1 file is read through one path, read-only) · AP5.

**v1 tests found:**
| Test file | What it covers | Reuse? |
|---|---|---|
| `tests/integration/db/contract/import-export.test.js` | idempotent re-import; round-trip keeps the `id` | **partly** — both cases, cut to v1-DB → v2-store |
| `tests/e2e/real-app/real-app-import.test.js` | upload via the UI | **no** — no UI, no HTTP here |

**v1 numbers (the bar):** measured on a **copy** of the real v1 DB after Q5: total rows, rows with
`valid_until` set, rows past `expires_at`, `pinned` rows, rows over a v2 limit (title 200, content 8000,
tags 20 × 100 chars), encrypted yes/no. Filled in here before approval.

## 2. Spec (the contract)

**Goal:** copy every v1 memory into the v2 DB once, with its dates, and give each a v2 vector — never write the v1 file.

**Behaviour:**
1. `npm run import:v1 -- --from <v1.db> [--dry-run]`. The target is the v2 DB from config (`SQLITE_PATH`).
2. **The v1 file is never opened in place.** The importer copies `<v1.db>` (plus `-wal` / `-shm` if they
   exist) to a temp folder and reads the copy, `readonly`. The temp folder is deleted on success **and** failure.
3. An encrypted v1 file (no `SQLite format 3` header) → stop with a clear message: "turn off
   APERIO_DB_ENCRYPT in v1, start v1 once, then import". No decrypt code in v2 (non-goal).
4. Rows selected: see Q2. Each row maps 1:1: `id, type, title, content, tags, importance, source,
   created_at, updated_at` are kept as they are. The other v1 columns are dropped (counted in the report).
5. One v2 transaction. An `id` already in v2 → skipped (a second run imports 0). A row that fails a v2
   check → **not written, listed in the report with its id and the field** (never silent).
6. After the commit, the existing `reindex()` (S2.4) embeds every imported row with the v2 model.
   An embedder failure leaves rows saved with no vector and says so; the next start's reindex fills them.
7. The report: `{ total, imported, skipped, rejected: [{ id, field, why }], dropped: { tier, pinned, … }, embedded }`,
   printed as plain text; `imported + skipped + rejected.length === total` is checked before the commit.
8. `--dry-run` does steps 2–5 and the check in 7, then rolls back. Nothing is written.

**Interface:**
```js
// src/store/import-v1.js — pure: no config, no argv, no process.env
importV1({ v1Path, store, embedder, log, dryRun = false }) → Promise<Report>
// src/store/memory-store.js — new, used only by the importer
store.importRows(rows) → { imported, skipped, rejected }   // keeps id + both dates; one transaction
// scripts/import-v1.mjs — reads argv + config, opens the store, calls importV1, prints the report
```

**Errors:** missing file, not SQLite, encrypted, no `memories` table, v2 DB not writable → one clear line and
exit 1, nothing written. A rejected row is not an error: it is in the report.

**Limits:** v2 store limits stay as they are (title 200, content 8000, 20 tags). Rows are read in pages of
500 (no full load into memory for a big DB). No new config key: the source path is a one-off CLI argument.

**Non-goals:** no JSON import/export (ledger: `later`) · no Postgres source · no decrypt · no wiki, sessions,
self-memory, jobs, vectors from v1 (v1 vectors are a different model) · no UI · no merge by content (dedupe is by `id` only).

**Keeps from v1:** one transaction, idempotent by `id`, a counted result. **Drops:** date reset, silent skip,
silent catch, the non-core tables.

## 3. Acceptance (becomes T2.12)

Fixture: a v1-schema DB built in the test from `tests/fixtures/v1-memories.sql` (the v1 `memories` table,
copied once from the tag — tests never call `git`). Every path is a temp folder (L-P03).
- [ ] N fixture rows → `imported === N`, every `id`, `title`, `content`, `tags`, `importance`, `source`,
      `created_at`, `updated_at` equal to v1.
- [ ] the v1 file's sha256 (and its `-wal` if any) is the same before and after; its mtime too.
- [ ] a second run: `imported 0`, `skipped N` (ported v1 "importAll is idempotent").
- [ ] a row over a v2 limit → in `rejected` with its id and field; the other rows still import; the sum check holds.
- [ ] every imported row has a vector with the v2 sig after the run (fake embedder); an embedder that
      throws → rows saved, `embedded 0`, the error logged once.
- [ ] a recall on an imported row's words finds it (store search, fake embedder).
- [ ] encrypted file (random bytes), not-SQLite file, missing `memories` table → clear error, v2 DB unchanged.
- [ ] `--dry-run` → report filled, v2 row count unchanged.
- [ ] the temp copy folder is gone after success and after a thrown error.
- [ ] Q2 rows (superseded / expired) are handled as decided and counted in the report.
- [ ] live, manual (developer): the real v1 DB copy → 0 lost rows, counts match §1, one sample recall finds an old memory.

## 4. Open questions (developer decides)

1. **Keep the v1 `id`:** **yes (my pick)** — a re-run skips by `id`, and old ids in notes still work. Or
   **new ids** — then a re-run makes duplicates unless we dedupe by content.
2. **Superseded and expired rows** (`valid_until` set / past `expires_at`): **import only current rows,
   count the rest in the report (my pick)** — v1 hid them from recall too. Or **import all** — then old, wrong
   facts come back into recall.
3. **Rows over a v2 limit:** **reject and list them in the report (my pick)** — you fix them by hand; no data
   is cut. Or **cut to the limit and mark the tag `imported-cut`** — nothing is left out, but text is lost.
4. **Ledger:** row "import/export" is `later`. This importer is a new one-way tool (TR3), not that feature.
   **Add a `core` row "v1 → v2 importer (TR3)" (my pick)**, or mark the existing row.
5. **Measure the bar now:** may the next session copy your real v1 DB to its scratch folder (read-only, then
   deleted) to count the §1 numbers? It reads your memories' text only to check lengths; nothing leaves the machine.
