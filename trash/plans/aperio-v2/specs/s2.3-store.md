## 1. v1 study (read at `archive/v1-final`)

**How v1 did it:**
- `db/sqlite/store.js` (842 ln) → `SqliteStore`: memories, inbox, wiki, settings, model facts, encryption, seeds, plus 6 mixins. `insert` / `update` / `delete` each end with `refreshCache()` (the whole table held in memory).
- `db/sqlite/search.js` (195 ln) → `recallMemories(db, {query, queryEmbedding, mode, …})`: vector KNN (`k = 60`) + FTS5, fused by reciprocal rank (RRF, constant 60). Falls back to FTS when there is no vector.
- `db/sqlite/mappers.js` → `ftsMatchQuery()`: quotes every token, so `21:00` or `-` cannot break FTS5.
- `db/sqlite/vecSupport.js` (354 ln) → loads `sqlite-vec`; with no extension it rewrites the vec0 tables into plain tables and repairs a DB that moved between machines.
- `db/migrate-sqlite.js` (67 ln) → applies `migrations-sqlite/*.sql` once each, one transaction per file. 14 files.
- `update` = tombstone the old row (`valid_until`) + insert a new row with a new id.

**Best parts (keep):** RRF hybrid query · token quoting in `ftsMatchQuery` · FTS5 external-content table with triggers · one transaction per migration, recorded in `schema_migrations` · FTS-only mode when `sqlite-vec` cannot load (L-C20) · rowid-keyed vector table.

**Bad parts (drop / fix):**
- **FTS joins tokens with AND.** A normal sentence almost never matches. Measured below: 0 of 12 sentence queries. Auto-recall (S2.6) searches with the user's sentence, so this would break the one rule.
- `refreshCache()` holds every memory in a module-owned array (AP6).
- God file, 842 lines + 6 mixins (AP7).
- Vector width `FLOAT[1024]` is hard-coded in a migration. That forced 354 lines of repair code.
- Vector cleanup lived in a trigger; a second path forgot it and left orphans (L-C13).
- KNN takes 60 rows and filters **after**; tombstoned versions eat the slots.
- 16 columns; `tier`, `lang`, `confidence`, `valid_from`, `valid_until`, `expires_at` serve features that are not core.

**Lessons that apply:** L-C13 (forget must delete the vector in the same operation) · L-C17 (signature per row) · L-C20 (no `sqlite-vec` → FTS still works) · L-P03 / TR15 (no path frozen at import) · L-C01 (sync SQLite blocks the loop: measure max, not p95) · L-C07 (few dependencies).

## 2. Spec (the contract)

**Goal:** one small SQLite store that saves, changes, deletes, lists and searches memories, by words and by meaning, and never leaves an orphan vector.

**Behaviour:**
1. `openStore({ path, dims, log })` opens the file, loads `sqlite-vec`, runs migrations, and returns the store. `path` and `dims` come from the caller (config, S2.2). The store reads no env and holds no module state (AP1, TR15). `path: ':memory:'` works for tests.
2. **Migrations:** `src/store/migrations/*.sql`, sorted by name, each applied once in its own transaction, recorded in `schema_migrations`. A second run does nothing. A failed file rolls back and throws with the file name.
3. **Schema (`001_memories.sql`):**
   - `memories(id TEXT PK, type, title, content, tags JSON, importance 1–5, source, created_at, updated_at, embedding_sig TEXT NULL)`.
   - `memories_fts` (FTS5, external content, `title` + `content`, `unicode61` tokenizer) + the 3 sync triggers from v1.
   - `memory_history(id INTEGER PK, memory_id, type, title, content, tags, importance, source, replaced_at)`, index on `memory_id`. No FTS, no vector.
   - `type` keeps the 9 v1 values, so the v1 import (S2.12) loses nothing.
4. **Vectors are derived data and are not in a migration.** At open, if the extension loaded, the store makes sure `vec_memories(rowid, embedding FLOAT[dims])` exists with the right width. If the width differs, it drops the table, recreates it, sets every `embedding_sig` to NULL, and logs one warning. If the extension did not load, it creates nothing and `store.vectorSupported` is `false`.
5. **`embedding_sig`** is an opaque text the caller gives with each vector (S2.4 defines it). NULL means "no vector". The vector row and the `embedding_sig` value change in **one transaction**, always.
6. **Update is in place, with history.** Same id, new `updated_at`. Before the change, the old row is copied to `memory_history` in the same transaction. Search and `list` never read that table. `history(id)` returns the old versions, newest first. If `title` or `content` changes, the old vector is deleted and `embedding_sig` becomes NULL in the same transaction, unless the caller passes a new vector.
7. **Delete** removes the row, its FTS entry (trigger), its vector and its history rows (code, same transaction). Forget means forget. It returns the deleted title, or `null` if the id does not exist.
8. **Search** `search({ query, queryEmbedding?, mode, limit, type?, tags? })`, `mode` = `auto` | `fulltext` | `semantic`:
   - Full-text: tokens are quoted (v1 `ftsMatchQuery`) and joined with **OR**; rank = `bm25`, title weight 4.
   - Semantic: KNN on `vec_memories`. The store saves every vector at unit length and searches with L2 distance, so the order is the cosine order (cosine in `sqlite-vec` measured 4× slower).
   - `auto`: both, fused with RRF (constant 60). A row that matches both ranks above a row that matches one.
   - No vector, or `vectorSupported` false → full-text only. No words left in the query → `list` order.
   - Each result has the memory fields + `score` (0–1) + `matched: ['fts'|'vec']`. Score meaning: full-text only = bm25 relative to the best row; semantic only = cosine similarity (absolute); both = fused rank relative to the best row.

**Interface** (async, so Postgres can come back behind the same shape; 11 methods):
```
insert(input, embedding?, sig?) → memory          getById(id) → memory | null
update(id, patch, embedding?, sig?) → memory      delete(id) → title | null
list({ type?, tags?, limit, offset, order }) → memory[]
search({ … }) → result[]                          counts() → { total, embedded }
setEmbedding(id, embedding, sig) → boolean        listNeedingEmbedding(sig, limit) → {id,title,content}[]
history(id) → { type, title, content, tags[], importance, source, replacedAt }[]      close()
```
`memory = { id, type, title, content, tags[], importance, source, createdAt, updatedAt }`. `insert` accepts an optional absolute `createdAt` (eval seeding, v1 import).

**Errors (AP5):**
- Bad input (missing title/content, unknown type, importance out of 1–5, tags not a string array) → `StoreError` that names the field. Nothing is written.
- `update` on a missing id → `StoreError('not found')`.
- Vector of the wrong length → `StoreError` with both lengths. The row is not written.
- `setEmbedding` when `vectorSupported` is false → returns `false`, writes nothing.
- Extension load failure → one warning through `log`, then FTS-only. Never a crash.
- Migration failure → throws with the file name. The DB is unchanged.

**Limits:** `limit` is clamped to 1–50 (search) and 1–200 (list). KNN candidate count 60. `title` ≤ 200 chars, `content` ≤ 8 000 chars, ≤ 20 tags. No cache of any kind (AP6). Sync SQLite calls block the loop, so the 10 000-row test reports **max** time. Files ≤ 500 lines each; target ≤ 450 lines for the whole store (v1: 1 458 in 4 files).

**Config keys added:** none. `SQLITE_PATH` exists. `dims` comes from the embedding step (S2.4); tests pass a number.

**Non-goals:** settings table (S3.6) · inbox / pending memories (S2.7) · embedding model and the reindex loop (S2.4) · the 5 tools (S2.8) · v1 import (S2.12) · Postgres · encryption · wiki · "as of" queries and history in search · tiers, pinning, expiry, duplicates merge · seeds · any change to `src/eval/` (a `v2-live` adapter comes with S2.5/S2.6).

**Keeps from v1:** RRF query, token quoting, FTS triggers, migration runner, FTS-only degraded mode — all proven by v1 tests.
**Drops from v1:** AND matching (10/24 → 22/24) · memory cache (AP6) · hard-coded vector width and its 354-line repair · the vector cleanup trigger (code does it, one path) · tombstone versions inside `memories` (history moves to its own table) · 6 non-core columns · mixins.

**Try it:** `npm run try:search -- "your sentence"` (`scripts/try-search.mjs`) loads `evals/memories.json` into an in-memory store and prints the top 5 with score and match kind. Full-text only until S2.4. It writes nothing to disk.

**Files:** `src/store/open-store.js` (open, migrate, vector setup) · `src/store/memory-store.js` (CRUD) · `src/store/memory-search.js` (search) · `src/store/migrations/001_memories.sql`.
**New dependencies:** `better-sqlite3`, `sqlite-vec` (both from v1).

## 3. Acceptance (→ T2.3)

- [x] ported (`contract/memories.test.js`): insert → `getById` roundtrip; missing id → `null`; delete returns the title, then `null`; `counts()` returns numbers.
- [x] update in place: same id, new `updatedAt`, FTS finds the new text and not the old text.
- [x] history: after 2 updates, `history(id)` has 2 rows, newest first, with the old text; `search` and `list` never return a history row; an update that changes nothing writes no history row.
- [x] delete removes the history rows of that memory.
- [x] `try:search` prints ranked rows for a sentence and creates no file.
- [x] update of `content` with no new vector removes the vector and clears `embedding_sig`.
- [x] **forget cleans the vector (L-C13):** after `delete`, `vec_memories` has 0 rows for that rowid. Teeth: remove the cleanup line → red.
- [x] full-text hit; semantic hit; hybrid ranks a both-match row above a one-match row.
- [x] **eval number:** full-text `hitRateAt5` on `evals/corpus.json` ≥ 20/24, train and holdout reported apart. Teeth: switch OR back to AND → red.
- [x] FTS safety (ported): queries `meeting at 21:00`, `foo-bar`, `"quoted`, `*` and an empty string do not throw.
- [x] unicode: a Cyrillic memory is found by a Cyrillic word.
- [x] migrations: an empty DB gets the schema; a second open applies nothing; a broken file rolls back and names the file.
- [x] no extension (ported, `vec-fallback.test.js`): with the loader forced to fail, open works, insert/update/delete work, `search` returns FTS rows, `setEmbedding` returns `false`.
- [x] width change: reopen with other `dims` → vectors empty, every `embedding_sig` NULL, one warning.
- [x] `listNeedingEmbedding(sig)` returns rows with NULL or a different signature only.
- [x] bad input: each error case in "Errors" throws a `StoreError` that names the field, and writes nothing.
- [x] 10 000 rows: hybrid top-5 search **max** ≤ 25 ms over 120 runs (mean and max printed); result count never above `limit`.
- [x] concurrent writes: 50 parallel `insert` + `delete` calls end with consistent `counts()` and 0 orphan vectors.
- [x] TR15: two stores opened with two paths in one process do not share rows.
- [x] `close()` releases the file (the temp dir can be removed; reopen works).

## 4. Decisions (developer, 2026-11-11)

1. **Driver:** `better-sqlite3` + `sqlite-vec`, as in v1. `node:sqlite` was rejected: experimental, and not proven with `sqlite-vec`.
2. **Update:** in place, and the old version goes to `memory_history`. Search never reads it. Lost history cannot come back; the table costs little.
3. **Columns dropped:** `tier`, `lang`, `confidence`, `valid_from`, `valid_until`, `expires_at`, `pinned`.
4. **Full-text joins tokens with OR.** Check it again on the first live baseline.
5. **`try:search` script** is in scope, so the developer can see ranked results before the UI exists.
6. **Carried to S2.6:** semantic search always returns the nearest rows, even far ones. Auto-recall needs a measured minimum score, or "no match" never happens.

## 5. Build results (2026-11-11)

| What | v1 | v2 |
|---|---|---|
| Full-text `hitRateAt5` (24 queries) | 10/24 (train 6/16, holdout 4/8) | **22/24** (train 15/16, holdout 7/8) |
| Hybrid top-5, 10 000 rows × 1024 dims | mean 8.3 / max 9.2 ms | mean 9.4 / **max 10.8 ms** (limit 25) |
| Insert 10 000 rows with vectors | 0.8 s (one transaction) | 1.5 s (one transaction per row) |
| Size | 1 458 lines, 4 files | 450 lines, 3 files + 60-line migration |

- 49 tests in `tests/store/`. Teeth drills run: no vector cleanup on delete → 2 red; OR back to AND → 3 red (hit rate falls to 10/24).
- **Changed during build:** cosine distance in `sqlite-vec` measured 11.7 ms against 2.8 ms for L2 at 10 000 rows, so the store keeps unit-length vectors and uses L2. Same order, 4× faster.
- **Open finding, not built:** common words ("what", "do", "in", "the") can lift a wrong memory to rank 1. Example: "what coffee do I drink in the morning" puts the coffee memory at rank 2. Dropping an English stop-word list moves top-1 from 20/24 to 21/24; top-5 stays 22/24. It is language-specific, so it waits for a decision, and for the semantic half (S2.4), which may fix it alone.
