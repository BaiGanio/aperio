## 1. v1 study (read at `archive/v1-final`)

**How v1 did it:**
- `lib/config.js` (589 lines) → `CONFIG`: 125 entries `{key, section, type, tier, show, default, help, liteDefault}` + groups, sections, UI categories, lite profile.
- `lib/config-resolver.js` → `applyConfigToEnv(store)`: at boot, **writes DB values into `process.env`**, so ~280 raw `process.env.X` reads see them. Records provenance in a module-level `Map`.
- `lib/config-sync.js` → `.env` parse, "unmanaged" var import, `shadowedEnvKeys()`.
- `scripts/gen-env-example.js` → `.env.example` + `docs/config-reference.md`, `--check` for CI.

**Best parts (keep):** one registry as the single source of truth · two tiers (0 = env only, 1 = DB-editable) · pure `sourceFor()` provenance rule · `.env` shadow notice (secrets named, never printed) · generator with `--check`.

**Bad parts (drop / fix):**
- Injection into `process.env` is the root of **AP1**: every module reads env, import order decides the value (L-C22, L-P03).
- Module-level `_sources` Map (AP6-shaped); module-level `EDITABLE_KEYS`/`TIER0` consts.
- Precedence key read from env **and** DB, plus a lite override — three rules for one switch.
- 125 keys, unmanaged-var import, groups/banners, UI categories: not core.

**Lessons that apply:** L-P03 (env frozen at import hit the real DB) · L-C22 (import order is a security boundary) · TR15 (config read through a function) · L-C25 (one lint block per rule, for the AP1 allowlist).

## 2. Spec (the contract)

**Goal:** one pure function turns (env, DB settings) into a frozen, typed config with provenance.

**Behaviour:**
1. `src/config/registry.js` — frozen array, ~20 entries `{ key, tier, type, default, secret?, options?, help }`. Types: `int`, `bool`, `select`, `text`, `path`.
2. `src/config/read-config.js` — `readConfig({ env, settings })` → `Object.freeze({ values, sources })`. **Pure, no module state.** It never writes `process.env`.
3. Precedence per Tier-1 key: `db` mode = DB → env → default; `env` mode = env → DB → default. Tier-0 keys = env → default; a DB value for them is ignored.
4. `APERIO_CONFIG_PRECEDENCE` is Tier-0: env only, default `db`. (v1 also read it from the DB; dropped.)
5. `loadConfig({ settings })` — the only boot entry: loads `.env` with Node's `process.loadEnvFile` (no `dotenv`), then calls `readConfig({ env: process.env, settings })`. Callers get config through `ctx` or by calling it. **No module-level config const anywhere** (TR15).
6. `shadowedKeys({ fileEnv, settings, mode })` — pure; boot logs one line per shadowed key, secrets by name only.
7. `scripts/gen-env-example.mjs` — writes `.env.example` from the registry; `--check` exits 1 if stale. Added to `npm run check`. Never writes `.env`.

**Initial keys (~20):**
- Tier 0: `APERIO_CONFIG_PRECEDENCE`, `PORT`, `HOST`, `SQLITE_PATH`, `APERIO_ALLOWED_PATHS`, `LLAMACPP_VENDOR_DIR`.
- Tier 1: `LLAMACPP_MODEL`, `LLAMACPP_PORT`, `LLAMACPP_CTX`, `LLAMACPP_SERVE_CTX`, `LLAMA_CACHE`, `EMBEDDING_MODEL`, `TRANSFORMERS_CACHE`, `RECALL_TOP_K`, `RECALL_TOKEN_BUDGET`, `SESSION_RETENTION_DAYS`, `LOG_LEVEL`.
- Later steps add their own keys to the registry, one test each. Defaults copied from v1 where the key exists.

**Errors (no silent fallback, AP5):**
- Bad value (not an int, not in `options`) → throws `ConfigError` naming key, layer and value (secret value masked). Boot stops.
- Unknown key in `settings` → `validateSetting(key, value)` rejects it on write; on read it logs one warning and is ignored.
- Missing `.env` → fine, env + defaults apply.

**Limits:** registry ≤ ~30 keys before a split. No cache, so no AP6 risk. Each file ≤ 500 lines.

**Non-goals:** settings store/table (S2.3 passes `settings` as a plain object) · settings route + UI (S3.6) · lite profile · unmanaged `.env` import · `docs/config-reference.md` · hot reload (restart applies) · encryption · cloud providers.

**Keeps / drops:** keeps tiers, provenance rule, shadow notice, generator `--check` (all tested in v1). Drops `process.env` injection (AP1 root), module-level maps (AP6), DB-settable precedence + lite rule (one switch, one rule), 105 non-core keys.

## 3. Acceptance (→ T2.2)

- [ ] `db` mode: DB beats env beats default (one key, all 3 layers set; then drop layers one by one).
- [ ] `env` mode flips DB and env; a DB-only key still applies.
- [ ] Tier-0 key ignores a DB value; source is never `db`.
- [ ] `sources` matches the v1 8-case matrix (ported from `config-schema.test.js`).
- [ ] Bad int / bad select → `ConfigError` with key name; secret value not in the message.
- [ ] Unknown key: `validateSetting` throws; `readConfig` warns and ignores.
- [ ] TR15 guard: change `env.SQLITE_PATH` after import → next `readConfig` returns the new path.
- [ ] Shadow cases E1–E2e ported from `config-shadow-warning.test.js`; secrets never printed.
- [ ] Generator: run twice → byte-identical; `--check` exits 1 after a registry edit, 0 after regen. Runs in a temp dir.
- [ ] Lint teeth: `process.env` in a planted file outside `src/config/` fails AP1; inside `src/config/` passes.
