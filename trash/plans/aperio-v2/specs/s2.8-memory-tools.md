## 1. v1 study (read at `archive/v1-final`)

**How v1 did it:**
- `mcp/tools/memory.js` (131 lines) registered **7** MCP tools in a child process: `remember`,
  `propose_memory`, `recall`, `update_memory`, `forget`, `backfill_embeddings`, `deduplicate_memories`.
  Zod schemas; ids are UUIDs.
- `lib/handlers/memory/memoryHandlers.js` ln 303–351: `updateMemoryHandler` re-embeds when title or
  content change, and the store **versions** the row: the old row is tombstoned, the reply gives a
  **new id**. `forgetHandler` deletes by id and returns the title.
- v1 had **no `list` tool**. `recall` with no query listed rows (`order: importance | recent`) and
  added a "more exist" footer.

**Best parts (keep):** update re-embeds changed text; forget returns the title it removed; errors
name the id; `order: importance | recent` for listing.

**Bad parts (drop / fix):**
- update gave a new id, so an id the model had seen went stale ("superseded — use its replacement
  ID"). v2 store keeps the id and writes the old text to `memory_history` (S2.3). Fixed by design.
- `forget` left orphan vectors (L-C13). v2 `store.delete` removes the vector in the same transaction (T2.3).
- The MCP child process and its transport. v2 runs tools in-process (S2.7 rev 3 `tool-loop.js`).
- `backfill_embeddings` and `deduplicate_memories` as model tools: the S2.4 reindex and the
  `remember` duplicate check (S2.7) do that work in code. `propose_memory` = inbox, `later`.
- `recall` doing two jobs (search and list): one tool, one job.

**Lessons that apply:**
- **L-M15** — prompt routing is tool routing. 2 → 5 tools may change when the model calls
  `remember` / `recall`. Re-run the S2.7 eval with 5 tools; report the change.
- **L-M04 / L-M22** — the tool array is fixed from turn 1. Adding 3 tools changes it **once**, not per turn.
- **L-C04** — a bad call gets a pointed hint: which field, and the right shape.
- **L-C13** — forget removes the vector too (already a T2.3 test; T2.8 checks it through the tool).
- **L-M02** — the model may not call `recall` / `list` to find an id first. Measured below.

**v1 tests found:**
| Test file | What it covers | Reuse? |
|---|---|---|
| `tests/unit/tools/memory.test.js` `updateMemoryHandler` (6 tests) | unknown id, no fields, title change, content re-embeds, no-vector path, tags-only no re-embed | **partly** — keep the cases; drop the MCP envelope, embedding queue, tags/importance |
| same, `forgetHandler` (2 tests) | deleted → title; unknown id → error | **yes**, cut to the v2 result shape |

## 2. Spec (the contract)

**Goal:** the model can fix, delete and browse its memories, with the same guards as `remember`.

**Behaviour:**
1. **`recall` now returns `id`** with each memory, so the model can pass it to `update` / `forget`.
2. **`update({ id, content?, title?, type? })`** — at least one field. New text gets the secret
   check (refused like `remember`) and a new vector; if the embedder fails, the old vector is
   removed and the S2.4 reindex fills it (store already does this). The id stays the same.
   No duplicate check on update.
3. **`forget({ id })`** — deletes the row, its vector and its history. Returns the title.
   Description: call it **only** when the user asks to forget or delete something.
4. **`list({ type?, order?, limit? })`** — newest or most important first. Returns
   `id, title, type, date` only, no content (keeps the tool result small). `more: true` when rows were cut.
5. **Tool order on the wire, fixed:** `remember, recall, update, forget, list`. 5 ≤ 6.
6. **System prompt +1 line:** "To change or forget a memory, find its id with recall or list first."
   Stays ≤ 1.5k tokens.

**Interface:** same shape as S2.7 — frozen `{ name, description, parameters, run(args, ctx) }`.
`ctx = { store, embedder, config, log }`, frozen by a key-snapshot contract test.
| Tool | OK result |
|---|---|
| `update` | `{ ok: true, id, message: 'Updated.' }` |
| `forget` | `{ ok: true, id, message: 'Forgotten: "<title>".' }` |
| `list` | `{ ok: true, memories: [{ id, title, type, date }], more }` |

**Errors** (all `ok: false`, never thrown — AP5, L-C04):
- missing / unknown id → `No memory with id <id>. Call recall or list to find the id.`
- `update` with no field → `Give at least one of: content, title, type.`
- secret in new text → same message as `remember`.
- bad `type` / `order` → name the field and list the allowed values.
- store error → the tool loop's `<name> failed: …` (already built).

**Limits:** `list` default `LIST_LIMIT` (new config key, default 20) and hard max 50; store cap 200
stays. Titles 200 chars (store). No new cache, no module state (AP6).

**Non-goals:** no confirm dialog for `forget` (no UI yet; S3 may add one through the return gate);
no undo; no tags / importance in tool args; no bulk forget; no MCP wrapper; no `backfill` / `dedup` tools.

**Keeps from v1:** re-embed on update; forget returns title; list order modes — they work.
**Drops from v1:** new id on update (stale ids); MCP child (cost, AP2-style transport code);
backfill / dedup / propose tools (code does it, or `later`).

## 4. Open questions

1. **Tool names.** Plan says `update`, `forget`, `list`. A small model may read `update` / `list` as
   vague. Option A: keep the plan names. Option B: `update_memory`, `forget`, `list_memories`.
   **Recommend A** — all 5 tools are memory tools, the descriptions say "memory"; the eval shows a problem if one exists.
2. **Ids.** Full UUID (36 chars) vs a short id. **Recommend full UUID** now; the eval's "right id"
   check measures copy errors. Short ids come only if that number is bad.
