## 1. v1 study (read at `archive/v1-final`)

**How v1 did it** — v1 had an inbox, but **no auto-capture**. The model had to choose to save:
- `mcp/tools/memory.js` → tool `propose_memory` ("use this when *you* notice something worth keeping"). `id/agent-rules/aperio-memory.md` told the model when to call it.
- `lib/handlers/memory/memoryHandlers.js` ln 422 → `proposeMemoryHandler()` → `store.insertPending()`. `source` came from `process.env.AI_PROVIDER` / `LLAMACPP_MODEL`.
- `db/migrations-sqlite/009_memory_inbox.sql` → table `pending_memories` (status `pending|approved|rejected`, `reviewed_at`, `session_id`).
- `db/sqlite/store.js` ln 459–531 → `insertPending`, `listPending`, `countPending`, `approvePending` (one transaction: check + insert + status flip), `rejectPending`.
- `lib/routes/api-memories.js` ln 185–225 → REST `GET /memories/pending`, `/count`, `POST /:id/approve`, `/:id/reject`.

**Best parts (keep):** approve is one transaction, re-guarded by `AND status = 'pending'`, so two clicks promote once · reject leaves no memory behind · list is newest first.

**Bad parts (drop / fix):**
- Capture depended on the model calling a tool. That is exactly L-M02: a 4–9B model will not do it reliably. It was also one more tool in the prefix (rule 7).
- `approvePending` inserts the memory with **embedding `null`**. An approved memory was invisible to semantic search until someone ran `backfill`. v2 embeds on approve (L-C13, L-C17).
- `source` read from `process.env` inside a handler (AP1).
- No duplicate check and no secret check before a row lands in the inbox.
- No bound: pending and rejected rows grow forever, and a rejected row keeps its full text forever (data kept past its use).

**Lessons:** L-M02 (code does the memory work) · L-M03, L-M04, L-M22 (stable prefix; one hybrid-model cache miss = 24× slower turn) · L-M20 (test the cold path: capture starts on an empty store) · L-M10 (train + holdout) · L-M11 (N = 5) · L-M19 (grade by code, not by a model) · L-M23 (check a threshold on chat-shaped text) · L-C13 / L-C17 (a vector and its signature go in with the row).

**v1 tests found:**

**v1 numbers:** none. v1 capture ran only when the model chose to call `propose_memory`, and v1 live runs were dropped (S2.1 decision 6). **v2 baseline today:** with capture off, the two cross-session scenarios (`uwh-cross-session-standup` train, `uwh-cross-session-pager` holdout) score **0/N by construction**: session B starts with an empty store, so recall has nothing to find. Capture must lift them off 0.

## 2. Spec (the contract)

**Goal:** after each finished turn, code finds statement-shaped facts in the **user's** text and puts them in an inbox. Nothing enters `memories` without an approval or a rule.

**Behaviour:**
1. **When.** After `turn_complete` (the reply is fully sent). It runs off the reply path, one capture at a time per session. It never delays the reply.
2. **Input.** The user's text of that turn only. Assistant text is not read (it can be wrong, and it is the model talking, not the user).
3. **Find candidates (code, no model call).** Split into sentences. Drop questions, sentences under 12 or over 400 chars, and chit-chat. Keep a sentence when a cue rule matches. Two cue kinds: **explicit** ("remember that", "for the record", "note that", "don't forget") and **statement** (change or plan: "from now on", "from next week", "moves to", "we decided"; preference or personal fact: "I prefer", "my … is", "I use"; rule: "if … escalates/goes to", "always", "never"). The cue list is one module with tests. At most `CAPTURE_MAX_PER_TURN` candidates.
4. **Secret check.** A sentence that matches a secret pattern (API-key shapes `sk-…`, `ghp_…`, `AKIA…`, a PEM header, `password:`/`token:` followed by a value, a hex/base64 run ≥ 32 chars) is **dropped**. It is never stored, not even in the inbox, and never logged. Only a count is emitted.
5. **Duplicate check.** Embed the candidate. (a) A stored memory scores ≥ `CAPTURE_DUP_SCORE` → drop (for example, the model's `remember` tool, S2.8, already saved it this turn). (b) A pending row has the same normalized-text hash or scores ≥ the same bar → **merge**: `seen_count + 1`, `last_seen_at` updated. (c) A rejected row has the same hash → drop. The user said no once; do not ask again.
6. **Propose.** Insert into `memory_inbox`: `type` from the cue (`preference`, `decision` or `fact`), `title` = first 8 words, `content` = the sentence, `source` = `capture`.
7. **Rule.** `CAPTURE_MODE`: `off` (no capture) · `inbox` (all candidates wait) · `explicit` (explicit-cue candidates are approved at once; all others wait).
8. **Approve** = embed (if the vector is not ready), then one transaction: re-check `status = 'pending'`, insert into `memories` **with its vector and signature**, set `status = 'approved'`, `memory_id`. The second of two concurrent approvals fails with `already reviewed`.
9. **Reject** = `status = 'rejected'`, and `title` + `content` are cleared. Only the hash stays, for step 5(c). Approve also clears them (the text now lives in `memories`).

**How capture stays out of the stable prefix** (the one rule: code does the memory work, the model only talks):
- Capture makes **no model call**. llama-server has one slot. A side extraction prompt would overwrite that slot's KV cache, so the next chat turn would reprocess the whole prompt (L-M22: 0.35 s → 8.2 s on Ornith).
- Capture writes only to `memory_inbox` / `memories`. It never edits the system prompt or the tool array. It adds no tool.
- An approved memory reaches the model only through the S2.6 recall block, **in a later user turn**, after the stable prefix.
- Test (below): a 3-turn run where capture fires and auto-approves on turn 1 keeps `stablePrefix` byte-identical on all turns, and the S2.6 exact client-token-prefix check holds.

**Interface:**
- `src/capture/capture-cues.js` → `findCandidates(text) → [{ sentence, kind: 'explicit'|'statement', type }]` (pure).
- `src/capture/secret-scan.js` → `hasSecret(text) → boolean` (pure).
- `src/capture/capture-turn.js` → `captureTurn({ text, store, inbox, embedder, config, emit, log }) → { proposed, approved, merged, dropped: { secret, duplicate, rejectedBefore, inboxFull } }`.
- `src/store/memory-inbox.js` → `createInbox({ db, store })` → `propose(c)`, `listPending({ limit, offset })`, `countPending()`, `approve(id)`, `reject(id)`.
- Migration `src/store/migrations/002_memory_inbox.sql`: `id, type, title, content, tags, source, cue_kind, content_hash, seen_count, status, proposed_at, last_seen_at, reviewed_at, memory_id`. Index on `(status, proposed_at DESC)` and on `content_hash`.
- Event `capture_done` with the counts above. **No text in events or logs.**

**Errors:** embedder unavailable → propose without the semantic check (hash check still runs), log `warn` once per session · store error → log `error`, emit `capture_failed`, the chat goes on (AP5) · inbox full → refuse the new candidate, emit `capture_inbox_full` (the oldest pending row may matter; never drop it silently) · approve or reject of an unknown or reviewed id → `StoreError` (`not found` / `already reviewed`).

**Limits (all config, AP1):** `CAPTURE_MODE` `explicit` · `CAPTURE_MAX_PER_TURN` 3 · `CAPTURE_DUP_SCORE` 85 (measured on the fixture before it is fixed, like `RECALL_MIN_SCORE`) · `CAPTURE_INBOX_MAX` 100 pending. Reviewed rows (hash only) are pruned past 1 000, oldest first. Capture step max ≤ 100 ms at 1 000 memories.

**Non-goals:** the inbox UI (S3.5) · socket messages (S2.11) · the `remember` tool (S2.8) · reading assistant text · languages other than English (the cue list is English; a Bulgarian list comes through the return gate with its own fixture) · model-based extraction · editing a candidate before approval · merging into an existing memory (update) · expiry, tiers, confidence.

**Keeps from v1 / drops from v1:** keeps the pending table idea, the atomic approve and the race test, because they were right. Drops the `propose_memory` tool (L-M02, rule 7), `process.env` in handlers (AP1), approve without a vector (v1 bug), and full text kept after review (data exposure).

## 3. Acceptance (becomes the tests)

- [ ] reused v1: insert → list → approve promotes, **with a vector**; semantic search finds it.
- [ ] reused v1: two concurrent approvals → exactly 1 memory, the other fails `already reviewed`.
- [ ] reused v1: reject → no memory, not listed, title/content cleared, hash kept.
- [ ] `CAPTURE_MODE=inbox`: a turn with facts writes **0** rows to `memories` (the "nothing without approval" rule).
- [ ] `CAPTURE_MODE=explicit`: "Remember that …" → in `memories`; a statement cue → in inbox only. `off` → nothing anywhere.
- [ ] secrets: each pattern in the fixture → 0 rows anywhere, 0 text in captured logs.
- [ ] duplicates: same fact twice → 1 pending row, `seen_count` 2 · fact already in `memories` → dropped · rejected text again → dropped.
- [ ] inbox full → refused + event, older rows unchanged · reviewed rows pruned past 1 000.
- [ ] embedder down → still proposed, hash dedupe works, one `warn`.
- [ ] stable prefix: 3 turns, capture + auto-approve on turn 1 → prefix bytes identical; client token prefix check passes.
- [ ] **Capture eval, offline (CI, deterministic):** new fixture `evals/capture.json`, user turns labelled `capture` (with required terms) or `skip`, split train / holdout. Bars: capture hit **train ≥ 18/20, holdout ≥ 8/10** · false proposals **≤ 1/12** skip turns · secrets proposed **0** · near-duplicates of `evals/memories.json` proposed **0** · step **max ≤ 100 ms** at 1 000 rows (N = 5, mean / sd / max).
- [ ] **Capture eval, live (gemma, N = 5):** the 2 cross-session scenarios, empty store, `CAPTURE_MODE=inbox` + approve all pending between sessions (stands in for the user's click). Bar: usedWithoutHint **≥ 4/5 each** with capture on, **0/5** off. Ornith: the developer runs it, as in S2.6.

## 4. Open questions (my pick first)

1. **How does code find candidates?**
   - **A (pick): cue rules in code.** No model call, so the KV cache is safe. Deterministic, cheap, testable in CI. Cost: English only, and it misses facts with no cue word. The holdout set shows how much.
   - B: one model extraction call at session end. It finds more, but it costs one cache rebuild per session, needs a model grader (L-M19), and small models drift on a cold start (L-M20).
2. **Default `CAPTURE_MODE`?**
   - **A (pick): `explicit`.** "Remember that …" is saved at once; everything else waits. The user asked to save, so a second ask is noise. Without it nothing is saved until the inbox UI exists (S3.5).
   - B: `inbox`. Nothing is saved without a click. Safest, but the feature does nothing in daily use until S3.5.
